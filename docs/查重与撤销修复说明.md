# 2.0.2：查重卡死、撤销卡死，以及"重做产生重复文件"

三个问题里最严重的是第三个。它不是卡顿，是**会真的多出一个文件**，所以先说它。

---

## 一、重做键还亮着，按下去文件变成两个

### 你看到的

把图1放进1号文件夹 → 撤销 → 再把图1放进1号文件夹 → **重做键仍然可点** → 点下去，1号文件夹里出现两个图1。

### 第一层原因：新操作没有截断重做分支

任何编辑器的规则都是：撤销之后又做了新的事，原来那条"可重做"的分支就作废了。这个规则缺了。旧记录留在重做栈上，按钮就一直亮，按下去会重放一个前提已经不成立的移动。

我在容器里复现了它：

```
移动后      src=[img2]        f1=[img1]  can_undo=True  can_redo=False
撤销后      src=[img1,img2]   f1=[]      can_undo=False can_redo=True
再次移动    src=[img2]        f1=[img1]  can_undo=True  can_redo=True   ← 这里就错了
```

现在：新操作提交时，同一个数据库事务里把重做栈清空，并释放那些记录占用的还原副本（否则还原区会一直涨）。修复后同样的操作序列，最后一行是 `can_redo=False`。

### 第二层原因（真正产生重复文件的那个）：两个线程同时写一个日记文件

这一层更要紧，而且和第一层是独立的。

分类操作跑在后台队列线程上（`background_queue` 默认开），但**撤销、重做、重命名、打标签都是直接在界面线程上跑的**。事务日记只有一个文件 `journal.json`。队列模块的注释写着"只用一个 worker，因为事务存储只允许一个日记"——但这条不变量被上面那四个入口全绕过了。

我写了个并发测试模拟界面线程边撤销边让队列跑分类，**25 个随机种子全部出错**：

```
error.pending_block_write                                   ← 两个事务抢同一个日记
FileNotFoundError: journal.json.writing -> journal.json      ← 两个线程用同一个临时文件名
```

第二条是关键。`atomic_json` 用固定的 `.writing` 后缀，A 线程把临时文件改名过去的时候，B 线程还在往它里面写。结果是**某个事务在没有日记的情况下继续改文件**——这时候崩溃或者下次启动做日记恢复，就会重放一个已经被别的路径做过的计划，于是同一张图落地两次。

现在：

- 事务存储加了一把锁，`run` 和 `recover` 全程持有。
- 引擎所有会改文件的入口（分类/跳过/重命名/回收/打标签/撤销/重做/忽略重复）都包在一个 `exclusive()` 里，**规划和执行在同一个临界区内**——计划里记录了每个文件当时的内容指纹，在一个正被别的线程改动的文件系统上算出来的计划，执行时就已经过期了。
- 同线程重入是**拒绝**而不是放行。`processEvents()` 会把你已经按下的键分发出去，可重入锁会让那第二个操作直接插进第一个中间，所以这里故意报 `error.busy`。
- `atomic_json` 的临时文件名带上进程号和随机串，失败时清理自己。

修复后同样的并发测试：25 个种子全部干净，没有日记残留，没有重复文件。

## 二、撤销和重做卡死

撤销本身只花 **3.6 毫秒**。卡的是它后面那行 `engine.rescan()`：

- 重新遍历整个源文件夹
- `metadata.clear_cache()` 把整个文件夹已经解析好的 EXIF 全部丢掉
- 重新过滤、重新排序整个队列
- 然后界面把胶片条和网格整个重填一遍

2 万个文件的文件夹：**519 毫秒**，而且在网络盘或者有杀毒软件盯着的时候会长得多。为了一个只动了一张照片的操作。

现在走增量：记录里本来就写着哪些文件动了，所以

| | 之前 | 现在 |
|---|---|---|
| 撤销后刷新（2 万文件） | 519 ms 全量重扫 | **14 ms**，一次目录都不列 |

做法是新的 `Engine.absorb(record)`：消失的文件从两个列表里摘掉，回来的文件用二分插回它在当前排序下该在的位置，然后只把这几行补进胶片条和网格。拿不准的情况（随机排序、复查模式、记录里没有路径信息）就返回 `None`，让调用方老老实实重建队列——宁可慢，不能错。

另外撤销/重做现在会**先等后台队列排空**才动历史（超过 0.3 秒才弹提示），并且所有能被快捷键触发的处理函数都加了忙碌保护。之前按住数字键让几次按键排进队列、紧接着按 Ctrl+Z，那些按键会在 `processEvents()` 里被分发出来，直接去改队列和两个视图。

## 三、查重卡死

`DuplicatesDialog.__init__` 里直接同步调用 `engine.find_duplicates()`——**在界面线程上，没有进度，没有取消**。2 万张照片要给每一张算感知哈希，每张要解码一次。按我在这里测到的单张成本推算，是 **6 分钟以上**，期间窗口完全不刷新。这不是卡顿，这是让人以为程序死了然后去强杀它——而强杀一个正在改文件的程序，就回到了第一节那个问题。

### 改了什么

**1. 扫描搬到工作线程**，带进度条、可取消、结果按模式缓存（切标签页不再重扫）。

**2. 并行哈希。** 解码和读盘都会释放 GIL，所以线程是有用的：

| | 之前 | 现在（2 核容器） |
|---|---|---|
| 相似扫描，首次 | 2.73 s | 2.21 s |
| 相似扫描，第二次 | 2.73 s | **0.03 s** |

首次的加速在这个 2 核容器里看不出来，你的机器核多，会接近线性。**第二次快 90 倍**这一项在任何机器上都成立——切标签页、忽略一组之后重扫，都是这一条路径。

**3. 精确查重不再通读整个库。** 原来是"大小相同 → 整个文件算 SHA-256"。一个 RAW 或视频库里"大小相同但内容不同"很常见，等于把硬盘从头读到尾。现在中间插一层：先只读**首尾各 64 KB** 加上大小做摘要。两个字节完全相同的文件必然在这上面一致，所以不会漏；只是大小相同的文件几乎不会一致，所以直接排除。

实测（125 张 0.9 MB 的图，其中 5 对是真副本）：

| | |
|---|---|
| 读取量 | **9.2%**（10.4 MB / 113.7 MB） |
| 完整哈希次数 | 10 次 / 125 个文件 |
| 真副本是否全部找到 | **是**，和逐个 SHA-256 的结果集完全一致 |

文件越大省得越多——首尾采样是固定的 128 KB，不随文件增长。

**4. 哈希缓存批量提交。** 之前每写一行 commit 一次，2 万行就是 2 万次磁盘刷写（容器里 5.1 秒，Windows 上更慢）。现在一次扫描一个事务：**0.33 秒**。读取端也加了批量预载，20 万次单行查询变成 50 次。

**5. 表格分块填充**，列宽固定。原来 `resizeColumnsToContents()` 要量过每一行每一格——几千行重复项时，光是填表就和扫描一样久。

**6. 跳过 8 KB 以下的文件**（图标、网页缩略图），它们只会让扫描更慢、结果更吵。

## 四、顺带修掉的、你还没撞上的问题

这些是我让一个子代理逆向审查 Qt 层时翻出来的，都已修复并加了测试：

- **撤销一次跳过/复制，那一行回不来。** 文件没动过，动的是"已处理"名单，我第一版的增量逻辑只看文件在不在 `all_files` 里，所以判定它"没变化"。（顺带说明：`all_files` 在移动后本来就不会被清理，所以移动的撤销也中招——这是我自己这轮改出来的 bug，已经修了并且补了会失败的测试。）
- **按评分排序时，插回的位置是错的。** 键函数只拿到了被动文件的评分，队列里其他行全被当成 0 星，二分查找就失去意义。
- **按"停止"会立刻重新开始同一次扫描**，只有关窗或者让它跑完才能脱身。
- **扫描中途关窗会让整个程序无限期冻住**：线程池是对话框的子对象，析构时会在界面线程上无超时 `waitForDone`，而排队中的取消信号又会在关闭后启动一次新扫描。
- **连拍组的"忽略"完全不生效**（`find_bursts` 根本没接收忽略名单），**相似组的"忽略"也时好时坏**（存进去的键带内容摘要，查回来的键是空的，两边永远对不上）。
- **元数据缓存没有锁**，而现在查重的 8 个工作线程和界面线程会同时读写它——`OrderedDict` 在迭代中被改会直接抛异常。
- **网格分块构建时插入一行会让它永久错位**（脏标记在构建开始前就被清掉了）。
- **队列任务失败时会把胶片条上所有的星标和色标擦掉**（只传了一个文件的装饰表，而 `set_paths` 是整表替换）。

## 五、测试

**297 个测试**（上一版 254）。新增的部分我都验证过"去掉修复它们会失败"——否则测试只是装饰：

- 去掉重做截断 → 3 个失败
- 去掉事务锁 → 并发测试失败（"第二个事务没有等待"）
- 去掉唯一临时文件名 → `FileNotFoundError` 重现
- 把 `absorb` 退回看 `all_files` 的版本 → 11 个失败
- 只退回按评分排序的键 → 1 个失败

并发测试是**确定性**的，不靠赛跑：拿住第一个事务不放，启动第二个，断言它必须阻塞。

`--selfcheck` 新增了 history 和 duplicates 两个阶段，会在你的真实磁盘上跑一遍并打印数字。

## 六、请你在 Windows 上确认

容器里装不上 PySide6（PyPI 被出口白名单挡着），所以 Qt 那层我只能静态审查，跑不起来。重新打包后：

```
python -m PyInstaller --noconfirm qingjian.spec
MediaSorter.exe --selfcheck
```

`interface` 那一项在这里是 FAIL（缺 PySide6），在你机器上应该是 PASS。

然后手动四条：

1. **你报的那条**：图1 → 1号文件夹 → 撤销 → 再放一次 → 看重做键是不是**灰的**。
2. **撤销速度**：在大文件夹里连按几次 Ctrl+Z，应该即时。
3. **查重**：Ctrl+D 打开，看到进度条；按停止，应该**真的停下**（不是重新开始）；再打开一次，应该很快。扫描中途关窗，程序不该卡住。
4. **忽略**：在相似和连拍两个标签页各忽略一组，重新扫描，它们不该再出现。

第 1 条要是还不对，把 `%LOCALAPPDATA%\Qingjian\logs` 里的日志发我。
