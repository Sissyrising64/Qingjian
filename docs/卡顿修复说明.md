# 轻拣 2.0.1 · 大文件夹卡死修复

**问题**：2.0 打开大文件夹会卡死，"轻量化快速看图"的手感没了。

**结论**：是我的回归，不是 Codex 那版改出来的。我对了一遍两个目录，
codex 只改了 7 行（网格创建顺序）和日志句柄，其余与我交付的字节一致。

---

## 一、根因

三处，第一处是主因。

### 1. 打开文件夹时给**每一个文件**排了缩略图解码任务

`_Browser.set_paths()` 对列表里的每一项调用 `cache.request()`，而胶片条和网格
**各建一份**。3000 张照片 = 6000 个解码任务，在打开的一瞬间全部入队。

而每个任务走的是**完整解码**：

```python
image = Image.open(path); image.load()      # 6000×4000 → 72 MB RGB
image = ImageOps.exif_transpose(image)      # 再复制一份 72 MB
image.thumbnail((168, 168))                 # 然后才缩小
```

实测单张 **260 ms / 峰值 72 MB**。乘以 6000，再乘以并发线程数，就是卡死加爆内存。

对比 1.0：它只解码当前这一张，而且用 `QImageReader.setScaledSize`，
让 libjpeg 直接按 1/2、1/4、1/8 从 DCT 系数出图。这就是"轻量化"的来源，我弄丢了。

### 2. 每按一次键都重列整个目录

找伴随文件时 `find_group()` 拿的是完整目录清单，而 `_commit()` 在每次操作后
清空缓存。20000 个文件的目录，**每按一次键重列一次，368 ms**。

### 3. 每次操作后重建两个完整列表

`_detach()` 调 `_refresh_browsers()`，把 20000 个 `QListWidgetItem` 全部重建，
一次按键两遍。

另有两处小的：状态栏每次刷新都遍历快照目录 stat；待复查计数把整张表拉出来数。

## 二、修法与实测

### 解码：交给 libjpeg 缩

```python
image = Image.open(path)
image.draft("RGB", target)   # libjpeg 按 1/2 1/4 1/8 直接出图
image.load()
```

| 单张 6000×4000 → 168px | 耗时 | 峰值内存 |
|---|---|---|
| 之前（完整解码） | 260 ms | 72 MB |
| 现在（draft DCT） | **17 ms** | **1.1 MB** |

感知哈希和清晰度评分再进一步用 `draft("L")`，让 libjpeg 直接输出灰度，
跳过 YCbCr→RGB：再省 20%。

### 只解码看得见的

- 列表只建条目，**不请求缩略图**；缩略图由滚动/缩放/显示事件触发，
  只取视野内 ± 12 行。
- 滚出视野的任务在执行前被丢弃（工作线程先问"还要吗"），
  丢弃后会通知视图重新请求，不会留下永远空白的格子。
- 胶片条只保留光标附近 ±80 项的窗口，不是整个队列。
- 网格在**第一次切过去**时才填充；超过 1500 项分块填充，带进度和取消。
- 解码线程池限到 2–4 个，不再是每核一个各持 72 MB。

| 打开一个 300 张照片的文件夹 | 排入的解码 | CPU |
|---|---|---|
| 之前 | 600 个 | 156 秒 |
| 现在 | 40 个 | 0.7 秒 |

**约 230 倍**。

### 目录只列一次

按文件夹建一份 `base stem → 文件` 索引，操作后**增量更新**而不是丢弃。

| 20000 文件的文件夹 | |
|---|---|
| `group_for()` 每次重列 | 368 ms |
| `group_for()` 用索引 | **0.2 ms**（稳态） |
| 打开整个文件夹 | 647 ms |
| 连续分类 30 次，单次中位 | **0.2 ms** |

索引不是无脑缓存：**每次查询都 stat 一下目录本身的修改时间**（一次 stat，不是列目录）。
如果目录被外部改过就重建。这一条很要紧——导入工具常常先落 JPG、几秒后才落 RAW，
缓存住的索引会看不见那个 RAW，于是照片搬走、RAW 留在原地。这是这个软件能犯的最严重的错误，
已有专门的回归测试（`test_a_sidecar_written_after_the_scan_is_still_found`）。

另外：FAT / exFAT 的时间戳只精确到秒，改动可能测不出来，所以刚被写过的目录（2 秒内）
一律重列，并且无论如何最多缓存 30 秒。这两条都是常数开销。

### 逐项增删，不再重建

`_detach()` 现在从每个列表里摘掉一行；失败的项按原位置插回。
状态栏的快照占用改成增量记账，待复查改成 `COUNT(*)`。

### 顺带补回：相邻图预解码

1.0 按 → 是瞬间出图的，因为它预解码了前后各一张。这个我漏了，现在补上：
`PreviewPrefetcher` 在后台线程解出下一张、下下张和上一张（只产 `QImage`，
`QPixmap` 仍然只在界面线程构造）。

### 顺带变快的

| | 之前 | 现在 |
|---|---|---|
| 按拍摄时间排序 300 张（第二次） | 148 ms | **6 ms**（拍摄时间进了持久缓存） |
| 相似查重 300 张（第二次） | — | **0.09 s** |

## 三、新增的回归测试

254 项（新增 12 项）。锁住的是**性质**，不是速度数字：

- `set_paths` 里不允许出现 `cache.request` —— 一旦有人加回去，测试红。
- 只有 `request_visible` 允许请求缩略图。
- 浏览 50 项，目录列表调用次数 ≤ 1。
- 连续分类 20 次，目录列表调用次数 ≤ 3。
- 查询 30 次快照占用，目录列表调用次数 ≤ 1。
- **扫描之后外部写入的 RAW 必须被发现并一起搬走。**
- 外部删除文件后分组仍然正确。
- 撤销后文件重新回到索引里。
- 视野窗口算术（`core/viewport.py`）11 项：边界、空列表、窗口必须包含光标、
  走完整个队列每步重建的行数不随队列长度增长。

## 四、仍需你在 Windows 上确认

我这里装不上 PySide6，界面层依旧只能静态保证。请跑：

```
MediaSorter.exe --selfcheck
```

自检新增了 **large folder** 这一项：建 1500 张图的文件夹，测打开耗时、
每项浏览耗时、每项归档耗时，超过阈值直接 FAIL。我这边的数字是
`open 35 ms · browse 0.2 ms/item · file 0 ms/item`。

然后请手动试这三件事：

1. 打开你那个大文件夹，看是否还卡；按住 → 连续翻，应当跟手。
2. 切到网格视图（`G`），滚动，缩略图应当边滚边出，不应整体卡住。
3. 找一个有 RAW 的目录，**软件已经打开着的时候**从外面往里拷一个同名 `.CR2`，
   然后分类那张 JPG，确认 RAW 跟着走了。
